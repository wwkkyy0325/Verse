# P1b — Desktop application

Goal: transcription without a terminal. Drag a file in, get a transcript out.

Design: `ui-design.md`. This file is the work breakdown.

Exit criteria: on a machine with a cached model, a user who has never seen a
terminal can open Verse, drop an audio file, watch it transcribe, and export an
SRT — with no step requiring a technical decision.

Stack: **Tauri 2** shell, **Svelte 5 + TypeScript** frontend built by Vite,
existing Rust crates unchanged behind it. Chosen over a native GUI toolkit for
a permissive licence and a hot-reloading dev loop; see `ui-design.md` §6 and
`THIRD_PARTY_NOTICES.md` for what it costs.

Ordering note: steps 1–3 exist to establish a working loop and to fail early on
the things that cannot be reasoned about — a window that will not open, a
port that collides, Chinese that renders wrong. Steps 4–6 build the testable
core before any real screen exists.

---

## [x] 1. Tauri shell and a window

`verse-app` became a Tauri crate: `lib.rs` holds the builder and the commands
the frontend calls, `main.rs` is a two-line entry point that hides the console
window in release, `tauri.conf.json` holds the window and bundle settings.

The frontend is `ui/`, scaffolded by `create-vite` with the `svelte-ts`
template and then stripped — counter component, demo assets and the template's
own global stylesheet all removed rather than left to rot.

One command so far, `hardware`, which returns the `HardwareProfile` the
pipeline would use. It is not filler: the degraded-hardware notice needs it,
and having it first meant the IPC boundary was exercised before anything
depended on it.

Icons are generated, not drawn by hand — `tools/make-icon.mjs` renders the
source PNG and `tauri icon` fans it out. Two bugs in that script were found by
looking at its output rather than reading it: supersampling offsets applied in
pixel units instead of normalised ones, which magnified and cropped the mark,
and a capsule distance function written in the rounded-box form, which is
`|dx| + |dy|` and therefore a diamond. Both are commented where they were.

**Verify:** ✅ `npx tauri dev` compiles (Tauri 2.12.1), opens the window, and
stays up. A temporary probe in the `hardware` command printed when the frontend
called it, confirming the webview loaded *and* that IPC works end to end. The
probe was then removed.

## [x] 2. Dev server address, single-sourced

The first attempt used Vite's default port, and the window attached itself to
an unrelated dev server already on it. Silent, and indistinguishable from the
app working.

`tauri.conf.json` is now the only place the port is written; `vite.config.ts`
reads `build.devUrl` for its own `server.port` and throws if the field is
missing. Three further guards, all explained in `ui-design.md` §6.1:
`strictPort` so a busy port is an error rather than a quiet relocation, an
explicit `127.0.0.1` host so `localhost` cannot resolve to `::1` against an
IPv4 listener, and a port chosen outside every default a developer is likely
to have running.

**Verify:** ✅ Port 17321 confirmed free. `npm run dev` reports
`http://127.0.0.1:17321/`, matching `build.devUrl` exactly. `npx tauri dev`
then loaded the frontend from it, which is the check that matters — the two
sides agreeing is not the same as the window finding the server.

## [x] 3. Component set and theme

The interface stopped being hand-ground. **shadcn-svelte** was taken wholesale:
eight components written into `src/lib/components/ui/` as source, plus Tailwind
v4 and a CSS-variable theme. The hand-written `tokens.css` is gone —
`ui-design.md` §4 explains why a shipped theme cannot be half-adopted.

Three things about that install are worth knowing, and each cost time:

- **The preset is a base62 blob generated by a website**, with no list of valid
  names and no way to ask. The CLI's own package was unpacked and
  `encodePreset()` called directly to produce `bdxlHoz4q`. Reproducible, unlike
  guessing.
- **shadcn's CLI reads `paths` from the root `tsconfig.json`**, but the Vite
  template puts the real config in `tsconfig.app.json` behind project
  references. The alias has to be declared in both, and nothing says so.
  TypeScript 6 also rejects the `baseUrl` every installation guide still
  includes.
- **The default font import is ~400 kB of glyphs this app will never draw.**
  Eight subsets — Devanagari, two Cyrillic, two Greek, Vietnamese, Latin
  extended. Pointing at the Latin file alone: 440 kB → 36 kB.

**Verify:** ✅ `npm run check` clean over 642 files, `npm run build` succeeds,
`npx tauri dev` opens the window. Whether the result *looks* right is step 4.

## [ ] 4. Chinese text and palette

The one thing that needs eyes, and the reason the specimen page is still up.

`ui-design.md` §4.1 argues the font question is largely settled by moving to a
web frontend, but the part that is not: shadcn bundles Noto Sans as a webfont
and **it carries no CJK glyphs**. The Chinese faces are named after it
explicitly, so 汉字 lands on 微软雅黑 rather than on whatever `sans-serif`
resolves to. Which face actually wins needs looking at.

**Verify:** 中文标点，包括「引号」「『双引号』」、——破折号、……省略号 all
render correctly, with no boxes or blanks. Latin and Chinese sit together
without the baselines fighting. The 15 px body text is legible without being
cramped. Both light and dark palettes are readable, switchable at the OS level.

## [x] 5. State model

Done ahead of the screens, deliberately: it is the half of the interface that
can be verified without looking at anything, and the steps that need a person
should not be queued behind work that does not.

`state.rs` holds `AppState`, `Screen`, `Working`, `Done`, `Failed`, `Recovery`
and `Effect`. No window, no webview, no framework types. Side effects are
returned as an `Effect` rather than performed, which keeps every transition a
pure function of state and input.

This paid for itself immediately: the frontend changed from a native toolkit to
a web one and `state.rs` crossed unchanged.

Two decisions the tests pin down that were not in the design document:

- **`Phase` was dropped.** The event vocabulary has no stage event, and
  inventing one for a label the user cannot act on is not worth a change to
  `verse-core`. `Working::has_output()` derives the distinction that was
  actually needed.
- **Cancelling does not return to the drop target immediately.** It sets
  `stopping` and waits for `JobCancelled`. Returning early would show an idle
  screen while the job wound down — a lie, and worse, an invitation to start a
  second job on top of the first.

**Verify:** ✅ 23 unit tests pass, covering both happy paths, four failure
kinds and their `Recovery`, a download landing after the user left, and the two
staleness rules — output from a job that is over is dropped, and progress for a
job that is not being followed is ignored.

**Opened and left alone:** `verse_core::ModelState` and
`Event::ModelStateChanged` are referenced only by a test in `verse-core`
itself; nothing produces them. The downloader has its own richer
`DownloadState`, and the interface reads that. Two model-state types exist and
one is unused — worth consolidating, but not as a side effect of this step.

## [x] 6. The bridge

Three files, each facing one direction.

`pipeline.rs` runs the same chain `verse transcribe` runs, publishing progress
to the bus instead of printing it. It is a **second copy** of that
orchestration, which is a real cost — the CLI should move onto this rather than
the two drifting apart.

`bridge.rs` holds a worker thread per job and one forwarding thread for the
life of the process. The forwarder drains the bus into `AppState` and, for
each `Applied`, emits an update to the window.

`state.rs` gained the `Applied` return: what visibly changed, so the caller
knows what to send. It carries no serialization, so the state machine still
knows nothing about the window.

**Verify:** ✅ 6 new tests in `bridge.rs` assert the **JSON shape** the
TypeScript reads. This is the only thing connecting the two halves, and
without it a renamed field compiles on both sides and fails at runtime as
blank values. The first run of it failed:

```
left:  {"end_ms": 3200, "start_ms": 1500, ...}
right: {"endMs": 3200, "startMs": 1500, ...}
```

`rename_all` on an enum renames its *variants*, not their fields. Every
timestamp would have arrived `undefined`. Fixed, and the trap is commented
where it was set.

## [x] 7. Window shows state

The mirror is live: the frontend subscribes to `verse://update`, applies each
update to its own copy, and renders. No debug readout was needed in the end —
the first real screen was small enough to build in one go.

## [x] 8. Empty screen

A full-window drop target with two states — idle, and highlighted while a file
is over it — plus a click-to-choose path through the system file dialog.

Drag-and-drop goes through Tauri's webview event rather than the browser's:
the webview is a native window, and an HTML drop target never sees a file
arrive from the operating system. The DOM events are still listened for, but
only to light up the target as the pointer crosses it.

**Verify:** pending a human. See step 9.

## [x] 9. Working screen (no export yet)

The header carries the file name, the recognised segment count, elapsed time
and 取消. The body is the transcript, filling in as it is recognised, with
timecodes.

Two deliberate departures from the plan:

- **No progress bar.** The decoder does not report a total length, and getting
  one means a probe pass over the file before decoding it. Elapsed time and
  segment count are honest and free.
- **Auto-follow stops when the user scrolls up.** Following new text is right
  until someone is reading; fighting them after that is worse than not
  following at all.

**Verify:** pending a human — drop a file, watch it fill in, cancel it
mid-run. The parts a machine can check are in step 6.

## [ ] 10. Done screen — export

The transcript is shown and selectable, but there is no way to write it out.
`verse-core::export` already renders SRT and text and is already tested; what
is missing is a button and a save dialog.

**Verify:** exporting writes a file a media player accepts as subtitles.
Auto-follow during `Working` stops the moment the transcript is scrolled up.

## [ ] 11. Failed screen

The reason, and one action per `Recovery` variant: retry, pick another mirror,
or choose a local model folder.

**Verify:** each failure path is triggered deliberately — a corrupt input, a
network-down fetch, a missing model — and each produces text naming something
the user can do.

## [ ] 12. NeedsModel screen

Download with progress, and manual import of an existing folder. This is where
P1a's deferred manual-import fallback finally earns its place.

**Verify:** with the model removed, dropping a file leads here; the fetch
completes and the pending job continues automatically. Pointing at a folder
that already holds a valid model skips the download entirely.
